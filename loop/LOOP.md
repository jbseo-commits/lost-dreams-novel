# 자율 집필 루프 절차

한 번 실행할 때 **최신화 확인 → 맥락 읽기 → 설계 → 집필 → 장면 가시성 검수 → 작품성 검수 → 역검수 → 기록 → 배포**를 한 화씩 수행한다.

기준은 단순히 ‘잘 쓴 웹소설’이 아니라 **휴대폰에서 빠르게 읽어도 장면이 보이고, 인물의 선택이 이해되며, 이 화를 빼면 작품이 약해지는가**다.

**현재 위치·기준 문서·고정 규칙·반복 금지 목록은 [현재 노선](CURRENT-LINE.md)에 있다. 0단계보다 먼저 읽는다.**

작업 규칙은 [AGENTS.md](../AGENTS.md), 설정값은 [config.md](config.md), 독자 이해·장면 가시성 기준은 [SCENE-VISIBILITY-GATE.md](SCENE-VISIBILITY-GATE.md)에 있다. 새 본편 실행 요청에는 [시작 프롬프트](forward-prompt.md)를 사용할 수 있다.

Claude Code에서는 [모델 분업](../docs/MODEL-ROUTING.md)을 함께 따른다. Codex/채팅에서는 해당 분업 문서를 따르되, 실제로 사용할 수 없는 reviewer/subagent를 사용했다고 기록하지 않는다. advisor는 독립 검수를 대체하지 않는다.

기본 실행은 한 회다. 작가가 구체적인 반복 계획을 승인한 자율주행은 [승인 후 자율주행](AUTODRIVE.md)을 따르며, 이 문서의 한 화 절차와 품질 기준을 회차마다 적용한다. 원고 수정 한도는 자율주행의 회차·재개 때 초기화하지 않는다.

## 0. 준비 — 오래된 상태에서 쓰지 않는다

1. `git pull --ff-only`로 최신 상태를 받는다. 충돌이나 미커밋 변경 때문에 실패하면 원고를 고치지 않고 이유를 보고한다.
2. `loop/config.md`를 읽는다.
   - 상태가 `정지`면 종료.
   - 목표 화수에 도달했으면 종료.
   - 종료 시각이 있고 KST 기준으로 지났으면 종료.
3. `CURRENT-LINE.md` 1절의 공개 본편·검수 완료(체인)·다음 집필 번호를 확인하고, `manuscript/`의 마지막 **공개 본편** 번호와 맞는지 대조한다. 다르면 `CURRENT-LINE.md`를 먼저 바로잡는다. 범퍼(`epNNN-1.md` 등)와 미추적 초안은 다음 본편 번호나 목표 달성 판단에 포함하지 않는다. 배포 여부를 확인하지 못했다면 Git 추적 상태와 공개 상태를 구분해 보고한다.
4. `loop/held/`에서는 이번 실행 범위에 맞는 원고와 보류 노트를 확인한다. FORWARD는 이어 쓸 본편의 품질 보류를 먼저 처리한다. 범퍼는 별도 BUMPER 작업으로 다루며, 생성 사유가 기각된 범퍼는 작가가 재검토를 지시하기 전까지 자동 재집필하지 않는다. 보류 파일이 있다는 이유만으로 본편 전진을 막지 않는다.
5. 자동 루프와 사람이 동시에 작업할 수 있으므로 **집필 직전과 최종 반영 직전 최신 HEAD를 다시 확인**한다.
6. 이미 공개된 화를 수정하는 별도 품질 작업과 새 화 자율 집필을 섞지 않는다. 공개 화 보강은 별도 브랜치에서 수행한다.
7. FORWARD / READER AUDIT / BUMPER는 [세 에이전트 협업 규칙](AGENT-WORKFLOW.md)대로 분리한다. 이미 공개된 본편과 같은 번호의 보류 사본은 자동 재집필 대상에서 제외한다.
8. 공개 최신 번호와 main의 원고 번호가 다르거나 다음 번호의 파일이 이미 있으면 그 원고 상태부터 확인한다. 공개 여부를 판단할 근거가 부족하면 새 번호를 임의로 정하지 않는다. 기존 파일을 덮어쓰거나 같은 번호를 중복 집필하지 않는다.

## 1. 맥락 읽기 — 필요한 것은 충분히, 전편 재독은 하지 않는다

반드시 읽는다.

- `AGENTS.md`
- `settings/` 전체
- `loop/config.md`의 작가 메모
- `loop/SCENE-VISIBILITY-GATE.md`
- `loop/story-so-far.md`
- 직전 3화 원문 전체 (체인 구간이면 `loop/held/`의 체인 원고가 직전 화다)
- 체인 원고의 `-notes.md` (새 제안·인계 사항)
- `loop/log.md` 최근 기록 3개
- `loop/CURRENT-LINE.md` 2절의 기준 문서 중 이번 화에 걸린 것: 해당 구간 기획의 `[통합검수 보강]` 블록, `MASTERPIECE-DECISIONS`, `EPISODE-QUALITY-MATRIX`의 해당 행, `MASTERPIECE-REVISION-QUEUE`의 미해결 항목

`story-so-far.md`가 최신화를 포함하지 않으면 빠진 화를 원문으로 확인해 먼저 보완한다. 단 체인 원고(미공개)는 `story-so-far.md`에 넣지 않고 원고·노트를 직접 읽는다. `story-so-far.md`의 '옛 원고(보류)' 표시 항목은 쓰지 않는다.

더 오래된 화가 필요할 때는 전체를 다시 읽지 않고 **필요한 장면·대사·수치만 원문 검색으로 확인**한다. 기억으로 연속성을 만들지 않는다.

### 1-1. 독자 물음표 선제 탐지

설계 전에 직전 3화를 독자처럼 빠르게 훑으며 다음을 확인한다.

- 대명사·`그거/그쪽/그 얘기/받다/두다/깨우다`의 지시 대상이 즉시 보이는가.
- 숫자가 무엇의 숫자인지 한 번에 알 수 있는가.
- 대사가 왜 나왔는지 앞 행동에서 추적되는가.
- 장면 전환 후 인물이 어디 있는지 알 수 있는가.
- 중심 사건에서 누가 무엇을 원했고, 무엇에 막혔으며, 어떤 행동 때문에 결과가 달라졌는지 원고만으로 설명할 수 있는가.

새 화는 이런 물음표를 새로 만들지 않는 방향으로 설계한다. 이 기준은 1화부터 적용한다. 반전의 배후나 인물의 숨은 의도는 남겨도 되지만, 현재 행동의 대상·당장의 선택지·결과까지 감추지는 않는다.

## 2. 설계 — 사건을 먼저 만들고 카메라는 함께 설계한다

`settings/09-narrative-arc.md`의 6부 구조에서 이번 화 위치를 확인하고 아래를 짧게 정한다.

1. **서사 목적 한 줄** — 무엇이 한 걸음 변하는가.
2. **구체 사건 한 줄** — 이번 화에서 실제로 무슨 일이 벌어지는가.
3. **즉시 비용/이득 한 줄** — 누구에게 무엇이 생기는가.
4. 장면 3~6개.
5. 이번 화의 핵심 선택 하나.
6. 마지막 문장의 여운.
7. 새 설정이 필요하면 `(제안)` 목록.
8. 이번 화를 눈에 보이게 할 **기존 또는 자연스러운 구체물 1~2개**.

중심 사건을 `원하는 것 → 막히는 이유 → 관찰 가능한 단서/압박 → 선택·행동 → 달라진 상태`로 짧게 연결해 본다. 빈 연결을 소품 묘사나 설정 해설로 메우지 않는다. 이것은 설계 확인용이며 모든 장면을 같은 순서로 쓰라는 형식이 아니다. 조용한 관계 장면도 서로를 대하는 방식이나 기대가 달라지면 서사 변화가 된다.

`CURRENT-LINE.md` 4절 반복 금지 목록과 3절 고정 규칙(호칭·'메시지 쓰고 지우기' 200화 전용 등)을 설계 단계에서 확인한다.

직전 3화와 **목표·충돌·선택·결과**를 비교한다. 요청서·심사·반론의 명칭이나 숫자만 바뀌고 같은 결론에 도착한다면 이번 화의 사건을 다시 설계한다. 반복 절차가 필요하면 이전에는 없던 손실·관계 변화·불가역적 결과를 독자가 경험할 수 있어야 한다. 새 사람이나 새 규칙을 추가한 것만으로 전진했다고 판단하지 않는다.

### 제21화 이후 사건 원칙

대략적인 감각은 **사건 70% → 선택 20% → 질문 10%**다. 기계적인 문장 비율이 아니다.

- 질문보다 사건이 먼저다.
- 철학적 질문은 한 화에 하나 정도만 남긴다.
- 한 계층에 유리한 선택이 다른 계층에 어떤 비용을 넘기는지 확인한다.
- 이미 말한 철학은 다시 토론하지 말고 다음에는 **달라진 비용·선택·관계**로 발전시킨다.
- 시스템을 설명하는 장면만으로 화를 구성하지 않는다.
- 세계관 설명은 행동을 이해하는 데 필요한 만큼 선택 전에도 제시할 수 있다. 규칙·숫자는 누가 무엇을 할 수 있거나 없게 되는지와 연결한다. 결과를 보여 준다는 이유로 독자가 선택의 의미를 끝까지 모르게 하지 않는다.

### 2-1. 장면별 카메라 초안

각 장면마다 아래 네 가지 중 필요한 것만 정한다.

- 어디인가.
- 누가 어디에 있는가.
- 무엇을 보고/만지고/들고 있는가.
- 장면이 끝날 때 무엇이 물리적으로 달라지는가.

모두 정할 필요는 없다. **장면을 그리는 데 필요한 최소치만** 정한다.

## 3. 집필 — 빠른 문체 + 보이는 장면

- 파일: `manuscript/epNNN.md`
- 첫 줄: `# 제N화. 제목`
- 분량: `config.md` 범위
- 짧은 문단, 대사 중심, 한 줄 한 문단의 기존 리듬을 유지한다.
- 시스템 화면 문구는 한 줄씩 `**굵게**`.
- 장면 전환은 `***`.

### 3-1. 장면 시작 규칙

새 장면이 시작된 뒤 **3~5문장 안에** 독자가 장소와 핵심 인물 배치를 그릴 수 있어야 한다.

단, 이미 시간·행동·소품만으로 충분히 보이면 억지로 배경을 설명하지 않는다.

### 3-2. 대화 규칙

- **모노의 목소리 표기(2026-10-07 작가 지시)**: 모노(개인 AI)가 소리 내어 하는 말은 사람 대사의 `“…”` 대신 `〈…〉`로 한 문단씩 쓴다. 굵은 글씨(`**…**`)는 뉴럴 피드·시스템 문구에만 쓴다. 회사·객실·통합 모델 등 모노가 아닌 기계 음성은 이 표기를 쓰지 않는다. 웹은 `〈…〉` 문단을 모노 전용 스타일로 그린다. 모노가 끼어들거나 경고·응답하는 말도 같은 표기로 통일한다(알림처럼 닫히는 문구여도 모노가 한 말이면 `〈…〉`).

대화는 빠르게 간다. 하지만 인물이 공간에서 사라지면 안 된다.

- 대사 8개 연속은 행동/시선/소품 앵커가 필요한지 확인하는 경고선이다.
- 화자 표시는 `말했다` 반복보다 필요한 행동으로 해결한다.
- 중요한 대사는 앞 행동 때문에 나와야 한다.
- `그거`, `그 얘기`, `그쪽` 같은 말이 장면의 핵심이면 지시 대상을 바로 추적할 수 있게 한다.

### 3-3. 숫자·제도 규칙

이 작품은 숫자와 시스템 화면을 적극적으로 쓰지만, 숫자가 무대의 전부가 되면 안 된다.

나쁜 흐름:

> 대사 → 개념 → 숫자 → 다음 대사

우선하는 흐름:

> 숫자/규칙 → 그것을 보는 사람 → 구체적인 선택 또는 생활의 변화

정책을 이해시키기 위해 해설을 늘리기보다 **달걀, 방석, 패, 열쇠, 계약서, 컵라면, 흙, 모종처럼 이미 장면에 있는 물건**이 결과를 짊어지게 한다.

소품이 등장했다는 사실은 이해의 증거가 아니다. 컵을 들고 물을 마시는 동작만 반복해도 제도의 비용이나 선택의 의미는 드러나지 않을 수 있다. **그 행동으로 누가 무엇을 얻거나 잃었는지** 원고에서 추적돼야 한다. 의미가 연결되지 않으면 소품을 더 넣기보다 사건의 원인과 결과를 고친다.

### 3-4. 중요한 선택의 한 박자

선택 직전/직후에는 필요할 경우 손, 시선, 종이, 화면, 자세, 이동 중 하나로 짧은 소화 시간을 준다.

감정을 설명하지 않는다. 행동이 감정을 대신하게 한다.

### 3-5. 서인의 통찰

‘천재라서 맞힌다’고 요약하지 않는다.

- 무엇을 물을지 압축한다.
- 무엇을 검증하지 않을지 선택한다.
- 제한된 TOKEN/시간/권한에서 직접 판단한다.
- 빠른 판단의 이익뿐 아니라 재확인 감소와 인간적 비용도 행동으로 보인다.

핵심 판단은 독자가 필요한 단서와 버린 선택지를 함께 볼 수 있게 한다. 정답·처리 시간만 나열하는 몽타주는 연결에 쓸 수 있으나, 이번 화의 결정적 선택을 대신하지 않는다.

### 3-5-1. 짧은 문장과 반복

짧은 문체를 `서인은 + 동사`의 동작 목록으로 흉내 내지 않는다. 컵·물·손·시선이나 같은 대답이 반복될 때는 새 정보, 압박, 관계 변화가 있는지 확인한다. 변화 없이 문장이나 분량만 늘리는 에코는 덜어낸다. 의도적 반복은 반복될 때마다 의미가 달라져야 한다.

행동과 상태가 앞뒤에서 충돌하면 전환의 원인을 쓰거나 잘못된 문장을 고친다. 주어·서술어가 맞지 않거나 뜻이 파손된 문장은 분위기·실험·모티프로 통과시키지 않는다. 분량이 부족해도 무관한 동작이나 새 제도로 채우지 않는다.

## 3-6. 웹 연출 (`pilot.html`)

원고가 초안 단계를 넘으면 핵심 순간 **하나**를 웹 연출로 만든다.

**발동 시점(2026-10-07 작가 지시)**: 세트피스는 읽는 도중에 뜨지 않는다. 화 본문이 모두 끝나고 독자가 마지막 문단을 지나 스크롤한 뒤에만 뜬다(한 화에 둘 이상이면 차례로). 페이지를 열자마자 뜨지 않도록 독자의 스크롤이 있어야 한다. `on`은 연출이 가리키는 장면을 기록하는 기준 문장으로 유지한다. 글을 가리거나 다시 설명하지 않고, 글이 끝낸 의미를 한 번 더 찌른다. 연출이 있는 화는 본문 끝과 다음 화 버튼 사이에 빈 구간을 두고, 연출이 닫힌 뒤에야 다음 화 버튼이 보인다(다음 화를 누르는 순간 연출이 겹치지 않게).

기존 규칙을 유지한다.

- `MAX`, 해당 화 `D`, 필요한 세트피스/CSS/함수, `KEY`만 최소 범위로 수정한다.
- 범퍼화는 본편 번호를 증가시키지 않고 `BUMP`에 연결한다.
- 기존 화 연출과 공통 엔진은 건드리지 않는다.
- 팝업은 원고의 숫자·이름·시각·대사를 사용하고 원고에 없는 사실을 만들지 않는다.
- 과정 → 절정 → 결과 순으로 움직인다.
- 같은 숫자 카운트/점 행렬/경고창 문법을 반복하지 않는다.
- 세트피스는 기본적으로 터치를 통과시키며, 인터랙션이 있으면 닫는 방법을 둔다.
- 빨리 넘기는 독자를 기다리게 하지 않는다.
- 웹 연출 때문에 원고 문장을 억지로 만들지 않는다. **원고가 먼저다.**

텍스트 연출의 멈춤(`0.8초.` 등), 강조 대사 `KEY`, 마지막 문단 여운 규칙도 유지한다. 남발하지 않는다.

## 4. 1차 검수 — 장면 가시성

작품성 점수보다 먼저 `SCENE-VISIBILITY-GATE.md`로 **PASS / CHANGES**를 판정한다.

핵심 질문은 여섯 개다.

1. 지금 어디인지 보이는가.
2. 누가 어디서 무엇을 하는지 보이는가.
3. 대사가 왜 나오는지 추적되는가.
4. 숫자/제도가 누구의 몸과 생활에 닿는지 보이는가.
5. 휴대폰에서 빠르게 읽어도 앞 문장을 되찾으러 가지 않는가.
6. 중심 인물의 목적·막힘·선택·결과가 원고만으로 연결되는가.

검수자는 먼저 원고와 직전 3화로 중심 사건을 자기 말로 재구성한다. 그 뒤 설정·요약을 대조한다. 설정집이나 집필자의 해설을 읽어야만 이해되는 연결은 원고의 통과 근거가 아니다. 막힌 지점은 실제 문장과 앞뒤 원인을 인용해 기록한다.

CHANGES면 원인에 맞게 수정한다. 화자·공간 누락은 필요한 최소 앵커로, 인과 누락은 단서·행동·결과의 연결로 고친다. 같은 사건의 반복은 장면 재설계가 필요할 수 있다. 모든 결함을 카메라 한 문장 추가로 해결하지 않는다.

### 4-1. 과잉수정 금지

가시성 검수의 목표는 모든 장면을 묘사하는 것이 아니다.

시장 2층, 벽시계, 노인정 담요, 패, 방석, 열쇠처럼 이미 장면을 지탱하는 구체물은 활용한다. 다만 특정 화수나 소품의 존재만으로 자동 PASS하지 않는다. 공간이 보여도 사건 인과나 반복 문제가 있으면 CHANGES다. 실제로 기준을 충족한 장면은 손대지 않는다.

‘더 잘 쓸 수 있다’는 이유만으로 수정하지 않는다.

## 5. 2차 검수 — 필수 통과 조건

집필과 분리해서 검수한다. 사용 가능한 환경에서는 별도 reviewer/subagent에게 원고를 쓰지 않은 편집자의 눈으로 보게 한다. 사용할 수 없는 환경에서는 독립 검수를 했다고 기록하지 않는다.

독립 검수가 불가능하면 자기 검수만으로 공개하지 않고 `검수 미실시`로 보류한다.

검수 직전 최신 원격 상태를 다시 확인하고 설정이 바뀌었으면 새 기준으로 본다.

검수 자료는 이번 화, 직전 3화, `story-so-far.md`, `settings/`, `SCENE-VISIBILITY-GATE.md`, 연출 변경분으로 제한한다. 더 오래된 화는 필요한 장면만 검색한다.

하나라도 어기면 불합격이다.

| # | 항목 | 불합격 기준 |
| --- | --- | --- |
| 1 | 설정 충돌 | `settings/` 확정 내용과 어긋남 |
| 2 | 반전 통제 | 5부 공개 전 최종 빌런 정체·기술 탈취·자녀 세뇌·인격 조정 배후를 확정 서술 |

## 6. 3차 검수 — 마스터피스 점수

각 1~10점. **모든 항목 8 이상, 평균 9 이상**이어야 통과한다.

점수는 편집 판단이며 독자 이탈률·상업 순위의 측정값이 아니다. 각 항목의 근거 문장을 인용하고 가장 약한 대목도 확인한다. 필수 조건이나 가시성·인과에 결함이 남으면 점수가 높아도 불합격이다. 이전 통과 로그나 집필자의 의도를 이번 원고의 증거로 쓰지 않는다.

| 항목 | 10점의 모습 |
| --- | --- |
| 장면의 필연성 | 모든 장면이 목적을 밀며 빼도 되는 장면이 없다 |
| 인물의 진실성 | 인물이 주제를 대신 말하지 않고 자기 이유로 움직인다 |
| 문장 | 설명조·상투구 대신 구체 행동과 감각으로 전달한다 |
| 대사 | 인물별 리듬이 다르고 말하지 않는 것이 있다 |
| 주제의 깊이 | 같은 질문을 반복하지 않고 새 비용/선택으로 한 걸음 판다 |
| 긴장과 여운 | 첫 장면이 붙잡고 마지막이 다음 화를 연다 |
| 연출 | 핵심 순간과 맞물리며 새롭고 모바일에서 아름답고 글을 반복하지 않는다 |

미달이면 지적된 결함만 우선 수정한다. 최대 3회. 부분 수정으로 안 되면 해당 장면을 다시 쓴다.

재검수는 `config.md`의 `재검수` 값을 따른다. `고친 부분만`이면 같은 reviewer에게 결함 목록과 수정 전후를 보내고, 바뀐 행동·소유·수치에 영향을 받는 앞뒤 구간도 함께 확인한다. 해결 판정은 수정 문장을 근거로 남긴다. 전체 재독을 매번 요구하지 않는다. 수정 한도는 게이트별로 새로 세지 않고 이번 실행의 원고 수정 합계 3회다.

## 7. 4차 검수 — 역검수(새 설정 발명 방지)

가시성 보강과 작품성 수정이 끝난 뒤 반드시 **반대로 한 번 읽는다**.

새 화에서는 설계·확정 설정과의 충돌, 근거 없이 건너뛴 전달·소유·시간을 확인한다. 정상적인 새 사건이나 행동까지 금지하는 단계가 아니다. 아래 '원문에 없는 사실' 금지는 이미 공개된 원고의 가시성 보강에 적용한다. 새 화의 미정 설정은 기존 제안 규칙을 따른다.

질문:

- 카메라를 설치한다며 원문에 없던 장소를 확정했는가.
- 벽 색, 책상 상태, 자세, 자리 배치 같은 의미 없는 세부를 발명했는가.
- 누군가 문서/파일/물건을 전달했다는 새 경로를 만들었는가.
- 시스템 UI의 색·지도·기계 동작을 새 설정처럼 만들었는가.
- 소품의 출처와 시간 연속성이 실제 앞 장면에 있는가.
- 같은 화면/지도/손/시선 비트를 기계적으로 반복했는가.
- 추가 문장이 원래 강한 문장을 약하게 만들었는가.

하나라도 그렇다면 **더 쓰지 말고 덜어낸다**.

이 단계의 원칙:

> 장면이 보이게 하는 데 성공한 뒤에는, 추가한 카메라가 이야기를 바꾸지 않았는지 확인한다.

## 8. 연출 동작 검사

브라우저 사용이 가능한 환경에서는 약 400×900 모바일 크기로 확인한다.

1. 1화 진입이 눌린다.
2. `pilot.html#ep{이번 화}`가 열린다.
3. `KEY`, 멈춤, 시스템 문구가 정상 표시된다.
4. 세트피스가 뜨고 사라진 뒤 본문 터치가 다시 된다.
5. 콘솔 오류가 없다.
6. 원고 목록에 이번 화가 보인다.

**연출은 언제나 마스터피스(2026-10-08 작가 지시).** 연출도 원고를 쓰지 않은 편집 검수자가 실제 화면(모바일 캡처)으로 7번째 항목 점수를 매기고, 8점 미만이면 공개하지 않는다. 2회 수정 후에도 연출이 실패하면 글만 먼저 공개하지 않고 그 화 전체를 보류한다(`연출 미달 보류`). 예전의 '글 우선 공개 + 연출 보류' 규칙은 폐지한다. 화면 캡처 전용 도구를 새로 만들지 않는다.

## 9. 보류

필수 통과 조건 또는 점수 기준을 3번 고쳐도 못 맞추면 공개하지 않는다.

- `loop/held/epNNN.md`로 이동. 같은 번호의 옛 파일이 있으면 덮어쓰지 않고 `epNNN-영문슬러그-YYYYMMDD.md`로 둔다(예: `ep051-standard-one-20261008.md`)

보류는 실패가 아니라 **낮은 품질의 자동 공개를 막는 정상 상태**다.

## 10. 기록 갱신

모든 검수를 통과한 뒤에만 기록을 갱신한다.

- `loop/story-so-far.md`: 3~5줄 요약 + 새 인물/수치/상태 변화
- `settings/05-open-questions.md`: 새 설정은 `자율 루프 제안` 아래 `(제안, 제N화)`
- `CHANGELOG.md`: 최상단에 추가
- `loop/log.md`: 결과와 실제 검수 상태 기록

작업 브랜치의 통과 원고는 `검수 완료·공개 대기`로 기록하고 `CURRENT-LINE.md` 1절(체인·다음 집필 번호)과 5절(인계)을 갱신한다. 51–55 검수에서 같은 동작이 반복 지적되면 4절 반복 금지 목록에 올린다. FORWARD가 이미 공개된 과거로 사용할 공식 요약과 범퍼 연속성은 main 반영 때 통합 담당자가 갱신한다. 공개 전 요약 초안이 필요하면 해당 작업 보고서에만 남긴다.

로그에는 장면 가시성도 별도 기록한다.

```md
## 날짜 시각 · 제N화 「제목」
- 결과: 공개 / 검수 완료·공개 대기 / 보류 / 건너뜀(이유)
- 분량: 공백 제외 N자
- 장면 가시성: PASS / CHANGES→PASS (수정 요약)
- 역검수: PASS / 제거한 과잉 카메라 요약
- 검수: 필수 조건, 7개 점수와 평균, 수정 횟수
- 독자 이해: 중심 사건의 목적→막힘→선택→결과 요약, 근거 문장 위치와 남은 결함
- 반복 점검: 직전 3화와 달라진 선택/결과 또는 관계
- 연출: 세트피스(편집 검수 점수) / 연출 미달 보류
- 새 제안: N개
- 배포: 성공(확인 주소) / 실패(이유) / 미실행 / 미확인
```

실제로 실행하지 않은 reviewer, 브라우저 검증, 배포를 했다고 기록하지 않는다.

## 11. 배포

현재 실행의 원격 쓰기·공개 권한을 먼저 확인한다. 작업 브랜치까지만 허용된 실행은 여기서 멈추고 `공개 대기·배포 미실행`으로 보고한다. `config.md`의 '바로 공개'만으로 다른 브랜치의 원고까지 병합하지 않는다.

1. `node scripts/build-manifest.mjs`로 목록 생성 확인. `manifest.json`은 직접 편집하지 않는다.
2. 커밋 메시지: `원고: 제N화 「제목」 (자율 루프)`.
3. push 실패 시 최신 상태를 받아 충돌 여부를 확인한 뒤 한 번만 재시도한다.
4. 가능한 환경에서는 GitHub Actions 웹 배포 성공과 공개 원고 주소를 확인한다.
5. 확인하지 못한 배포는 ‘성공’이라고 쓰지 않는다.

## 12. 공개 화 품질 감사 모드

작가가 실제 독서 중 캡처·물음표·“머릿속에 안 그려진다” 피드백을 주면 새 화 집필과 별도로 이 모드를 사용한다.

### 순서

1. 캡처를 **증상 데이터**로 본다.
2. 해당 원문과 앞뒤 맥락을 읽는다.
3. 문제를 분류한다.
   - 목적·선택지·사건 인과 부족
   - 같은 절차·결론 반복
   - 공간/배치 부족
   - 화자/지시어 불명확
   - 숫자/정책의 인간 결과 부족
   - 중요한 대사의 인과 부족
   - 희곡화
   - 모바일 원인→반응 거리
4. 먼저 구간 전체를 audit하고, **문제 장면만 선별**한다.
5. 원인에 맞게 수정한다. 화자·공간 누락은 최소 보강하고, 인과나 사건 재설계가 필요한 문제는 카메라 편집으로 처리하지 않는다. 작가가 허용한 공개 화 수정 범위를 넘으면 문제와 제안을 남긴다.
6. 수정 구간을 연속으로 다시 읽는다.
7. 마지막으로 역검수해 과도한 카메라·새 설정을 제거한다.

### 감사 모드의 핵심

- PASS인 화는 수정하지 않는다.
- 여러 화가 같은 문제라고 가정해 일괄 리라이트하지 않는다.
- 18~31화 감사에서 확인한 것처럼, 시스템 비중이 높아질수록 몸과 공간이 사라지는지 특히 본다.
- 구체물이 실제 선택과 비용을 짊어지는 장면은 좋은 기준으로 보존한다. 특정 구간 전체가 성공했다는 과거 평가를 면제 조건으로 삼지 않는다.
- 범퍼 추가는 `BUMPER-CONTINUITY.md`의 생성 게이트로 판단한다. 본편의 지시어·인과·반복 문제는 범퍼를 끼운다고 해결되지 않는다. 공개 본편 수정은 별도 작가 지시 범위에서 한다.
- 실제 독자 캡처에서 반복된 물음표는 다음 새 화 집필 규칙으로 승격한다. 일회성 땜질로 끝내지 않는다.

---

## 하지 않는 것

- `index.html`, `app.js`, `style.css`, `scripts/`, `.github/`는 자율 집필 중 고치지 않는다.
- `pilot.html`은 연출 규칙의 허용 범위만 수정한다.
- 이미 공개된 화를 자율 집필 루프가 임의로 고치지 않는다. 공개 화 감사 모드는 별도 브랜치/작업으로 한다.
- `settings/`의 확정 내용을 임의 변경하지 않는다.
- `loop/config.md`를 자율 루프가 임의 변경하지 않는다.
- 독자가 이해하기 어렵다는 이유로 세계관을 작가 해설로 풀어 쓰지 않는다.
- 장면이 안 보인다는 이유로 배경 묘사를 대량 추가하지 않는다.
- 검수 점수를 맞추기 위해 문장을 덧칠하지 않는다.
